# Price Truth — architecture, framework choices and NFRs

This document explains how the application is built, why each framework and library was chosen over the alternatives, and how the non-functional requirements are met and measured. The measured figures quoted here come from `reports/current/` and `reports/model_evaluation.json`. They are regenerated by `scripts/review.py`, never edited by hand.

## 1. What the system does

A shopper picks a product (Amazon or Flipkart listing) and enters the price they see. The app answers five questions on one scrolling dashboard:

| Question | Method | Data |
|---|---|---|
| Is this price in line with similar listings? | Gradient-boosting regression with Tree SHAP explanation | Real listings only (21,267) |
| Is the discount genuine? | 30-day reference-price rule (EU Omnibus 2019/2161 Art. 6a) **and** a logistic-regression classifier | Simulated daily histories and labels, calibrated to Indian research |
| Is now a good time to buy? | Position of the quote in the last 90 days, the sale calendar and a gated next-day forecast | Simulated histories; real Open Prices for food |
| Where is it cheapest? | Total cost across 8 platforms including delivery thresholds and platform fees | Simulated offers anchored to the listing's price |
| Which pack is better value, and has it shrunk? | Unit-price normalisation; cited shrinkflation cases | User input; 10 cited real cases + 5 simulated |

## 2. System overview and data flow

```text
                OFFLINE (build time)                                   ONLINE (each request)
 datasets/amazon/*.csv ─┐                                   browser ──HTTPS──► Streamlit server (app.py)
 datasets/flipkart/*.csv┴► data.py ─► processed/catalogue.csv            │  st.navigation (top menu)
                                         │                               ▼
                                         ├─► model.py ─► artifacts/price_model.joblib   views/dashboard.py
                                         │                                               │
 assumptions.json + MoSPI CPI ─► synthetic.py ─► datasets/final/*  ◄──── same seeded     ▼
                                         └─► authenticity.py ─► artifacts/discount_model.joblib
                                                                  dashboard.py (presentation only)
 Open Food Facts / Open Prices APIs ─► external.py / price_api.py      │ calls domain modules:
        (bounded, cached, validated)        │                          ├─ model.assess (+SHAP)
                                            ▼                          ├─ synthetic.reference_check, offers_for
                         datasets/external/ (cache + archive)          ├─ authenticity.assess_discount
                                                                       ├─ history.timing_signal, forecast.*
                                                                       ├─ calculations.compare_packs, shrink_change
                                                                       └─ exports.assessment_pdf
```

**Request path for one price check:** the dropdowns select a catalogue row. `price_inputs` pre-fills today's price, which comes from the seeded history for that listing. `analyse()` then calls `model.assess` (estimate, calibrated range, SHAP values), `synthetic.reference_check` (30-day rule), `authenticity.assess_discount` (classifier probability and contributions) and `synthetic.offers_for` (platform offers). `present.kpi_cards` turns those results into the six headline cards and the sections render the charts. Every computation is cached per product and price, so scrolling and re-rendering never repeat it.

## 3. Module boundaries (separation of concerns)

| Layer | Modules | Rule |
|---|---|---|
| Entry and navigation | `app.py`, `views/*.py` | One line per page: load cached resources, call one page function |
| Presentation | `dashboard.py`, `ui.py`, `workspace.py`, `market_ui.py`, `theme.py` | Layout and widgets only; never computes a business number |
| Presentation logic (pure) | `present.py` | Turns results into words and cards; no Streamlit import; fully unit-tested |
| Domain | `model.py`, `authenticity.py`, `synthetic.py`, `calculations.py`, `history.py`, `forecast.py`, `observations.py`, `offers.py`, `catalogue.py` | Pure functions over pandas data; validated inputs; raise `ValueError` with a user-readable message |
| Data access and integration | `data.py`, `external.py`, `price_api.py`, `evidence_store.py`, `cache.py`, `exports.py`, `resources.py`, `paths.py`, `logs.py` | Files, HTTP, caching, PDF, logging |

Dependencies point downwards only: domain modules never import Streamlit, so they can be unit- and mutation-tested in isolation. Eight domain modules are under mutation testing.

## 4. Data design

There is **no database server**, by design:

- **Catalogue and model artifacts** are read-only, versioned files (`datasets/processed`, `artifacts/`) loaded once per server process with `st.cache_data` / `st.cache_resource`. A database would add an operational component without adding a capability, because nothing is written at run time.
- **User observations** stay in the browser session (`st.session_state`). Users download and re-upload them as CSV. This keeps the app account-free, so it stores no personal data. This was a team decision on 7 October; persistence (e.g. Postgres) is listed as future work.
- **External API responses** are cached as atomic JSON files with a timestamp. Corrupt or wrong-product cache entries are treated as misses.
- **Provenance** is a column on every dataset row (`real` / `synthetic`), and its meaning is documented in `datasets/final/DATA-CARD.md`.

Main entities: *listing* (platform, product id, name, category group, subcategory, listed and selling price, rating, rating count, brand, variant, observed date, provenance); *daily history* (listing key, date, price, MRP, sale event); *offer* (listing key, platform, price, delivery fee, platform fee, total, availability); *observation* (product id, variant, store, currency, date, price, quantity, unit, source URL).

## 5. Framework and library choices

Each row compares the chosen tool with the alternatives considered, against this project's requirements: a data-science team working in Python, an explainable ML core, a working demo, free hosting and strong testability.

### Application framework

| Option | For | Against | Decision |
|---|---|---|---|
| **Streamlit 1.57** | Same language as the models; reactive widgets; built-in caching (`cache_data`, `cache_resource`), session state, file upload and download; official `AppTest` harness for UI tests; free HTTPS hosting on Community Cloud | Re-runs the script on each interaction (mitigated with caching and `st.fragment`); limited low-level layout control (handled with a scoped CSS layer) | **Chosen** |
| Flask / FastAPI + React | Full control of the UI; API reusable by other clients | Two codebases and languages; more security surface (CORS, sessions, auth); about 3× the build effort; needs separate hosting | Rejected for scope: no second client is planned |
| Plotly Dash | Python, good charts | Callback wiring grows quickly with linked dropdowns; weaker built-in testing harness | Rejected |
| Django | Mature, ORM, admin | Built around a relational DB and server-side templates the app does not need | Rejected |

### Machine learning

| Need | Chosen | Alternatives considered | Why |
|---|---|---|---|
| Price model | scikit-learn `HistGradientBoostingRegressor` on log(1+price) | Median baseline, Random Forest, XGBoost/LightGBM | It had the lowest validation mean absolute log error (0.259 vs 0.264 RF, 0.279 baseline) and handles missing ratings natively. Gradient boosting libraries such as XGBoost/LightGBM give a similar model with an extra compiled dependency |
| Uncertainty | Calibrated residual radius (conformal-style) | Quantile regression, bootstrapping | One fitted model; held-out coverage 89.8% for a 90% target |
| Verdict gate | At least 30 training listings in the same platform + subcategory; otherwise the platform + category group (labelled a rough guide); otherwise no verdict | Always give a verdict | Avoids confident verdicts where the model has seen few similar products; the fallback cut "no verdict" from 20% of listings to under 1% |
| Explanation | SHAP `TreeExplainer` | LIME, permutation importance | Exact, additive per-prediction values for tree models; the dashboard converts them to % effects that add up to the estimate |
| Discount model | Logistic regression | Gradient boosting classifier | Higher validation average precision (0.267 vs 0.227), the selection criterion; also a higher ROC AUC (0.883 vs 0.874) and a lower Brier score (0.049 vs 0.054, better calibrated). Its coefficients explain themselves |
| Data handling | pandas + NumPy | Polars | The team knows them; data size (≈ 0.8 M rows) fits in memory |
| Persistence | joblib | pickle, ONNX | Standard for scikit-learn; only locally built artifacts are loaded (no uploaded pickles) |

### Supporting libraries

| Need | Chosen | Alternatives | Why |
|---|---|---|---|
| Charts | Plotly | Altair, Matplotlib | Interactive hover tooltips (a design requirement), native in Streamlit |
| PDF export | ReportLab | WeasyPrint, fpdf2 | Pure Python with no system libraries, so it works in the slim Docker image and on Community Cloud |
| HTTP | requests | httpx | Synchronous calls with explicit timeouts are enough; no async needed |
| Hosting | Streamlit Community Cloud (+ Dockerfile) | Render, Hugging Face Spaces, VPS | Free HTTPS, deploys on every push; the Dockerfile keeps other hosts open |

### Quality tooling

| Purpose | Chosen | Alternatives | Why |
|---|---|---|---|
| Tests | pytest + Streamlit `AppTest` | unittest, Selenium-only | Fixtures and parametrisation; AppTest runs the real pages offline in CI |
| Coverage | pytest-cov (statement + branch) | coverage CLI | Same run as the tests |
| Mutation testing | mutmut 3 | cosmic-ray | Simple configuration in `pyproject.toml`; scope is the 8 domain modules |
| Lint | Ruff | flake8 + isort + pyupgrade | One fast tool replaces several |
| Complexity | Radon (CC, MI, raw, Halstead) | lizard, wily | Standard ranks A–F, as the rubric requires |
| Security (SAST) | Bandit | Semgrep | Python-specific, no account needed, JSON report |
| Browsers and load | Playwright | Selenium, Locust | One tool drives Chromium, Firefox and WebKit, downloads files and runs the concurrent-user load test with real browsers |

### Dependency policy

- `requirements.txt` pins only the **direct** runtime dependencies (`==`). Each one is imported by the application: numpy, pandas, scikit-learn, shap, joblib, streamlit, plotly, requests, reportlab.
- `requirements-dev.txt` adds the review tools with exact versions.
- `requirements.lock` pins every transitive package for reproducible Linux builds. It is generated with `uv pip compile requirements.txt --python-platform linux`.
- CI installs into a clean virtual environment and runs `pip check`.

## 6. Non-functional requirements

| NFR | How it is met | Evidence |
|---|---|---|
| **Performance** | Catalogue and models load once per process; a background thread warms SHAP and the PDF engine at start-up. Per-quote results are cached (`run_assessment`, `listing_history`), and the pack and shrinkflation sections are `st.fragment`s, so they never re-run the analysis | `reports/current/performance.json` (assessment latency), `load_test_*.json` (concurrent real-browser users), `browser_check.json` (time to an analysed dashboard) |
| **Security** | No secrets in code (none are needed; CI uses only GitHub's token). Every input is validated: prices must be positive with selling ≤ MRP, barcodes must be 8–14 digits, CSV uploads are capped at 2 MB / 10,000 rows with strict schema, dates, currency and HTTPS source checks, and are imported atomically. Outbound links go only to allow-listed retailer hosts. HTML is escaped before rendering. Only locally built model files are loaded. The Docker image runs as a non-root user | Bandit SAST in every review (`reports/current/bandit.json`, fails on medium/high); `tests/test_observations.py`, `tests/test_review_fixes*.py` |
| **Reliability & logging** | Structured JSON logs (`price_truth.logs`) for API calls (host, status, duration), assessments (status, duration), rejected inputs and warm-up failures. Failures are predictable: API failures fall back to clearly labelled saved responses, invalid inputs show a message instead of an exception, and the forecast declines when the history cannot support it. Cache writes are atomic. There is a health endpoint, a Docker health check, and a 15-minute uptime probe after deployment | `tests/test_logs.py`, `tests/test_search.py`, `uptime.yml` |
| **Maintainability** | Layered modules, functions at Radon rank A/B, docstrings throughout, regression tests for every review finding | `reports/current/radon-*.json`, coverage and mutation reports |
| **Usability & accessibility** | One dashboard, plain-language verdicts that don't rely on colour, hover explanations on every headline figure (also on keyboard focus), focus styles, reduced-motion support, high-contrast source badges. axe-core WCAG A/AA finds no serious issue in the app's own markup; the remaining findings are inside Streamlit components | `browser_check.json`; `docs/USABILITY-STUDY.md` (study kit) |
| **Portability** | Runs on Windows, macOS and Linux (UTF-8 I/O, LF line endings enforced); Docker image built and health-checked in CI | `.gitattributes`, `checks.yml` |
| **Scalability** | Stateless server apart from per-session state; heavy objects are shared across sessions. Scales out by running more container replicas behind a load balancer; the free tier is a single small instance, and the load test reports where it saturates | `load_test_*.json` |

## 7. Testing strategy

1. **Unit tests** cover every domain module and `present.py`, including edge cases and invalid input.
2. **Regression tests** cover each code-review finding (`tests/test_review_fixes*.py`).
3. **UI tests** use `AppTest`: every page renders, the dashboard dropdowns, price changes, validation, the unit comparison, the food-to-pack transfer and the user guide. They run offline.
4. **Mutation testing** of the eight domain modules checks that the assertions actually catch changes in logic. Surviving equivalent mutants are justified in `docs/MUTATION-SURVIVORS.md`.
5. **Browser tests** run the real flows in Chromium, Firefox and WebKit, check three viewports and run axe-core.
6. **Load tests** run concurrent real browsers against the hosted URL.

## 8. Known limitations

- Catalogue prices are historical (Amazon January 2023, Flipkart 2015–16); "today's" price is their CPI-adjusted simulation.
- The discount classifier learns the generator's rules: its accuracy measures recovery of the simulation, not detection of real fraud.
- The price model uses the listed MRP as a feature, so an inflated MRP raises the estimate; the discount check exists to counter this.
- There are no accounts or server-side persistence; observations live only for the session.
